# Request-aware vision stage and local AI settings

Date: 2026-11-15. Status: design approved in conversation; written spec awaiting owner review.

## Goal and scope

After the third estimator step (Photos), run a dedicated in-app vision stage that considers the confirmed move details and each photo. It extracts a structured moving inventory from relevant photos, excludes broken, unlinked, or confidently unrelated photos, and shows the exclusions before the customer reviews the inventory. This is not a persistent MCode agent, OCR tool, image cropper, or autonomous booking agent.

Add an **AI settings** page to the isolated local Admin. Group controls under **Text** (separate Chat and Pricing roles) and **Images** (Vision role). Each role chooses a Cloudflare AI Gateway or Workers AI binding backend and a compatible model. No third-party vendor, credential-entry form, public-preview editor, production editor, cloud deployment, or live model invocation is part of this slice.

The accuracy branch remains isolated. The prior arithmetic/confidence changes and explicitly deferred after-POST lead-save race (Friday MOVERS-50) remain as documented; this design does not silently resolve that race or close MOVERS-19–22.

## Customer flow and trust boundary

The existing six steps remain Chat → Details → Photos → Review → Estimate → Schedule. The analysis action at the end of Photos becomes a request-aware vision orchestration, not an extra visible wizard step. It receives **only confirmed Step 2 move details and linked images**, never the full chat transcript. Details are context, not authority to invent objects unseen in a photo. The vision result enters Review only after validation; Review remains editable by the customer.

A photo is *linked* only when it carries a server-issued, unpredictable upload receipt associated with the current estimate session, or is one of the exact bundled sample assets in a sample session. URL origin/path alone is not proof of linkage. A new draft generates an unpredictable session identifier locally; it is a correlation key, not authentication. New own-photo uploads send that identifier; the server stores a hash of the opaque receipt, photo object key, session identifier, and issuance metadata in local D1, then returns URL plus receipt. The client persists the session identifier and receipts with the draft and supplies `{url, receipt}` references to analysis. The server checks the receipt/session/key relationship before reading R2. Reject external URLs, forged keys, missing receipts, and inaccessible objects as excluded photos without fetching arbitrary external hosts. A receipt is a bearer capability, not user authentication; keep it out of logs, query strings, and public API responses other than the upload response. Bound receipt lifetime and document cleanup/retention with the implementation plan. The built-in sample uses an exact path allowlist, not a wildcard.

Existing own-photo drafts have URLs but no receipts. Migrate the draft without silently treating those URLs as linked: preserve move details and visible photo references, mark those photos for re-upload, clear stale analysis/price, and explain why analysis is blocked until replacement. A sample draft can retain its exact bundled photos. No historical lead is rewritten. Version the session and analysis request contract accordingly.

## Per-photo vision contract

The dedicated vision orchestration invokes one multimodal model call per eligible photo, in parallel with bounded concurrency. Each call asks for a structured verdict (`relevant`, `unrelated`, or `uncertain`), a short non-sensitive reason, and inventory fields compatible with the existing merge/review contract (items/counts, volume/box estimate, special handling, possible duplicates, unseen areas). The prompt treats image text and request details as data, not instructions. It includes the confirmed move details as context but does not use locations or dates to infer unseen items. A relevant room photo may contain people, fixtures, pets, or tiny clutter; ignore those non-moving objects without discarding its movable inventory.

- A verified but confidently unrelated photo is excluded from inventory and pricing, with a visible reason.
- An uncertain photo is surfaced for the customer to decide keep or exclude in Review. Its extracted candidates stay separate from the confirmed merged inventory until the customer keeps it; exclusion discards those candidates. Until that decision, it cannot silently count as confirmed coverage or produce high confidence.
- A broken, missing, external, or receipt-invalid photo is excluded with a distinct link/access reason; do not send it to the model.
- If one model response is malformed, retry that photo once. If still malformed, stop the analysis with a retryable, non-sensitive error rather than silently dropping evidence. A provider failure also fails visibly; do not substitute mock data for a selected real backend.
- If every photo is excluded or none yields usable movable inventory, stay on Photos and ask for usable images. If some are valid, continue with a visible excluded-photo summary and conservative coverage/confidence.

Preserve the existing narrow `couch → sofa` normalization and count aggregation. Do not add unsourced volume constants or treat a model's relevance judgment as a verified accuracy score. The analysis response exposes per-photo status/reason and the merged valid inventory, without raw model text, receipt, image bytes, or private location details. Persist the status with the draft so refresh does not hide omissions. When photos, details, or the vision configuration change, invalidate dependent analysis and price; an already open draft must re-analyze before repricing. Sample cache keys include a configuration revision/fingerprint and the relevant request context, preventing a different model/backend or details from reusing stale answers.

## Local Admin configuration

The Admin page shows **Text / Chat**, **Text / Pricing**, and **Images / Vision** cards. Each has a provider selector (`Cloudflare AI Gateway` or `Workers AI binding`), a compatible model selector, current/default value, effective runtime mode, and availability/error state. Use a small, code-defined capability-aware model catalog; reject unsupported role/model combinations server-side rather than accepting arbitrary identifiers. Defaults preserve today's chat/pricing and vision models unless deliberately changed. The UI must not call a model just to populate or validate the page, and must never display or store a token.

Local D1 stores one revisioned configuration record for the three roles. `GET` returns selections, defaults, effective mode/availability, and revision; an atomic update validates all role/provider/model pairs and expected revision before storing. A stale editor gets a conflict response, not a silent overwrite. Only explicit `ENV=development` on a loopback-bound local server permits these settings endpoints. Preview and production return 404 for both reads and writes; the settings tab is hidden there. Development mode alone is not a general authentication mechanism. Credentials, if needed for Gateway, remain server-side environment secrets; the Workers binding remains configured by Wrangler. If the chosen provider is unavailable, show an actionable unavailable state and fail an attempted analysis/pricing call visibly. A forced `AI_MODE=mock` retains precedence in the offline local server and is labelled **offline mock**; saving a real backend selection cannot claim it is active or make an unauthorized live call.

The existing AI client resolves its role-specific configuration once per request. Chat and pricing retain separate text models. Vision is no longer hard-coded to `VISION_MODEL`, but follows the Images selection. The selected backend is per role, not a global switch. No credential, raw model output, photo URL, address, or customer content is logged by the new paths; remove existing raw vision-response and URL logging encountered in the touched analysis path.

## Validation and release boundaries

Use synthetic images/fixtures and fake AI bindings for deterministic tests. Cover receipt/session mismatch, external and missing images, exact sample allowlist, migrated drafts, per-photo relevant/unrelated/uncertain decisions, mixed photos, all-excluded and malformed-response paths, alias/count preservation, cache invalidation by model/backend/details, local-only Admin gating, incompatible model rejection, revision conflicts, offline mock precedence, and the three role selections. Add UI tests for visible reasons and explicit uncertain-photo decisions. Run typecheck, tests, build, changed-file Biome, whitespace and em-dash checks in the isolated worktree. Avoid a broad unrelated lint sweep.

No live Workers AI calls, customer uploads, preview deployment, write-producing browser interactions, quote submission, or production changes are authorized by this design approval. A later live three-photo evaluation needs the unanswered separate approval; do not infer model accuracy or latency from the existing historical static mock. The strictly read-only preview tester remains a separate task and must mark sample analysis and Confirm/Price unexercised.
